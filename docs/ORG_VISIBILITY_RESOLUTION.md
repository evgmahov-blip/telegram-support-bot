# Организация клиента, видимость заявок и обязательное решение при закрытии

Задача: `support-bot-org-visibility-resolution-20261106` (база `43b5e57ab4858f0c08dfec3d798a0acdaee63722`).
Статус: кандидат; не развёрнут, не слит, не выпущен.

Связанные источники (не дублируются и не меняются здесь):

- `support-bot-organization-architecture-20261026` — архивная архитектура организаций; только контекст дизайна, не утверждённый источник полномочий.
- PR37 / `ainok-org-scoped-ticket-list-20261106` (`2890e0cb782d906e750349bf5ce1b914c4a3bb95`) — отдельная, не подключённая read-only основа списка заявок владельца организации для сайта. Здесь не используется и не активируется.
- PR36 / `support-engineer-result-ui-verification-20261105` — отдельная UI-канарейка ИИ-инженера; её интеграция и контроллер здесь не изменены.

## 1. Организация клиента (заявленная)

- Профиль клиента `ClientProfile` хранится по паре «платформа + пользователь» (`messenger`, `userid`). Это не реестр организаций.
- Первый `/start` в личном чате Telegram или первый запрос, который создал бы новую заявку, сначала просит название организации (2–120 символов, одна строка, с буквами/цифрами). Заявка до ввода не создаётся; клиенту прямо сказано, что сообщение пока не отправлено.
- Ответы в уже активной заявке организацией не блокируются.
- Меню клиента: «🏢 Организация» → «✏️ Изменить организацию» с «✖️ Отмена». Ожидание ввода хранится в БД с версией (переживает перезапуск; устаревшая кнопка отмены отклоняется).
- Значением организации может стать только обычный текст: команды (`/…`), callback-кнопки и медиа не принимаются.
- Новая заявка сохраняет снимок `declared_organization`. Изменение профиля прежние заявки не меняет.
- Это идентификационные данные со слов клиента: не подтверждённое членство, не OrgRef и не права. Видимость и роли от неё не зависят. Ненулевые канонические заявки организаций и маршруты основы PR37 не активируются.
- Вне Telegram (Signal, веб-виджет) организация не собирается — поведение прежнее.

## 2. Видимость: свои и общие заявки

- Общая заявка — без исполнителя (`assigned_to = null`) или явно сделанная общей (`common_visible = true`). Остальные — личные у владельца.
- Инженер видит свои и общие заявки (открытые и закрытые одинаково). Руководитель и администратор видят всё, как и раньше. Незарегистрированные пользователи не видят ничего.
- Проверка выполняется до чтения содержимого: деталь (`tc:open`), история (`tc:h`), решение (`rs:view`), `/ticket`, `/open`, списки и их пагинация (фильтр в запросе к БД).
- «🤝 Сделать общей» / «🔒 Сделать личной» на карточке: только владелец, руководитель, администратор; CAS по владельцу; событие `ticket.visibility_changed` в истории.
- Явный возврат в общие («Сделать общей» в личной карточке или в предложении, `tc:share` / `rt:common`) в той же CAS-записи создаёт `common_return_notice`. Если при этом создана новая общая карточка, она и есть запись в ленте. Если прежняя карточка только отредактирована, в группу/тему поддержки уходит отдельное сообщение «Заявка возвращена в общие» с номером и кнопкой «Открыть заявку» (`tc:open:N:n`), без текста, файлов и контактов клиента. Кнопка открывает новую панель и не затирает запись. Запись считается опубликованной только после того, как Telegram вернул id сообщения. Если Telegram явно отклонил отправку, периодический `runWorkflowChecks` повторяет её (не больше 5 попыток). При неизвестном результате (сетевая ошибка, брошенный claim) повтора нет, чтобы не было дублей. Если заявку снова взяли до публикации, запись помечается `superseded`.
- Общий чат группы показывает только общие данные. Канонические карточки личных заявок в группе показывают номер, статус и инженера — без клиента, организации и текста. Деталь, история, решение, «Мои заявки», «Все активные», «Закрытые» по личным заявкам отправляются только в личный чат сотрудника с ботом.
- Личный чат сотрудника — поверхность только для чтения: `/start` открывает панель «свои + общие»; действия остаются на карточке в группе.
- Новые сообщения, правки и файлы клиента по личной заявке отправляются только владельцу в личный чат. Если личный чат недоступен (бот заблокирован или не запущен), в группу уходит только уведомление без содержимого; повторной рассылки в группу нет.
- Подсказки ответа/заметки и подтверждения отправки по личной заявке не называют клиента; текст заметки не дублируется в группу; ответы не зеркалируются в родительскую группу.

### Ограничения (точно)

- Уже отправленные в группу сообщения нельзя сделать секретными фильтрами. Они сохранены; массового удаления нет.
- Текст, который инженер сам набирает в общей теме (ответ клиенту или заметка через подсказку), виден участникам группы. Бот этот текст не дублирует.
- `ai-draft` (при `use_llm` или `auto_triage`) по-прежнему публикует черновик в группу; панели ИИ-инженера (`ae:*`) открываются в группе. ИИ-интеграция и контроллер намеренно не менялись (PR36). В образце конфигурации эти функции выключены.
- HTTP API событий и вебхуки интеграций — не поверхности сотрудников; фильтр видимости к ним не применяется.

## 3. Обязательное решение при закрытии

- «🔒 Закрыть» и `/close` (ответом на сообщение заявки) запускают один и тот же поток: причина → что сделали → как проверили (необязательно, «⏭ Без проверки») → предпросмотр с автором → «✅ Закрыть заявку» / «✏️ Изменить» / «✖️ Отмена».
- Неизвестная причина записывается только явным выбором «❔ Причина не установлена» (`не установлена`); автоматически ничего не подставляется.
- Для личной заявки ввод идёт в личном чате владельца с ботом; для общей — в рабочей теме.
- Используются существующие `ResolutionIntent` и версии `TicketResolution` (режим `close`), без второго хранилища.
- Порядок при подтверждении: проверка прав и того же владельца → запись версии решения (CAS по `base_version`, защита от повтора по токену) → закрытие CAS по статусу и владельцу с записью `closure_resolution_version` в той же операции → завершение намерения. Сбой записи решения оставляет заявку открытой, а подтверждение — повторяемым; смена владельца, повтор кнопки или чужое более новое решение не закрывают заявку и не перезаписывают решение.
- Клиент получает только прежнее уведомление о закрытии; причина и работы остаются внутренними.
- Решение видно в карточке («📘 Решение»), в истории («Заявка закрыта (решение, версия N)») с автором и временем; ранее сохранённые решения доступны и после повторного открытия.

Обходы закрыты:

- старые кнопки «Да, закрыть» только снимают устаревшее подтверждение и ничего не закрывают;
- `/clear` (массовое закрытие) отключён;
- `auto_close_tickets` и `auto_close_after_days` не закрывают заявки (пишут в журнал), т. к. без участия инженера нельзя указать причину и работы;
- `allow_user_close`: `/close` клиента записывает просьбу `ticket.close_requested` и уведомляет владельца (общую заявку — в группу), но не закрывает.
