# Инженеры: кандидат и приёмка 17.11.2026

Задача AOR: `support-bot-engineers-rbac-20261117`. Изолированный worktree;
доверенный checkpoint: `e72be3e2b8d0fd74f941cd3f2a2b257d04f2b58e`.
Production VM3902, Telegram и реальные роли не изменялись. VM4090 — клиент GUI.

## Изменение

Существующий раздел `staff-name-editor` расширен: вход из личной панели,
пагинация, карточка с состоянием, подключение, подтверждение уровня и состояния,
откат. Роли остаются `admin/supervisor/agent` из `staff_roles`.
Настроенные display-name overrides в MongoDB сохранены; их редактор не заменён.

Идентичность подключения берётся только из `forward_origin.type=user` Telegram:
администратор пересылает текстовое сообщение с видимым автором, сверяет имя и
числовой ID и подтверждает. Скрытый автор, бот, username и введённый ID
не подходят. Это проверка Telegram-идентичности, а не трудоустройства:
администратор отдельно проверяет человека. Новый сотрудник — отключённый agent.
Потом администратор выбирает уровень и отдельно включает доступ. Инженеру
необходимо самому открыть бот и нажать /start для получения личных сообщений.

Изменения состава пишутся в существующий YAML, вместе с `team_settings_history`
(actor/time/before/after). Проверяется хеш всего файла; используется общий с
routing settings `.routing-lock`, временный файл, fsync и atomic rename.
Конфликт и повторное подтверждение отклоняются. Кеш меняется после rename.
Откат — новая проверяемая и аудируемая запись; подключённая идентичность
сохраняется отключённой, история не удаляется. Lock после аварии автоматически
не крадётся: требуется штатное восстановление оператором после проверки писателя.

Отключение запрещено при открытых/ожидающих заявках и outstanding routing offers.
Сначала руководитель/администратор передаёт их существующим механизмом или
контролируемо возвращает в общие. Отключение не меняет историю/видимость заявок.
Владелец защищён; изменение собственного уровня/состояния запрещено; снять
последнего действующего администратора нельзя. Supervisor не управляет командой.
Текущая роль проверяется при командах, callback и вводе. Старые slash-команды
дополнительно проверяют действующую роль; moderation требует assign, broadcast
требует manage_team; reopen проверяет владельца и routing version через CAS. Контекст группы сам по себе больше
не выдаёт staff authority. Старые поля session сбрасываются на каждом обновлении.

FIFO read/write barrier охватывает Telegram middleware: смена команды ждёт
завершения выполняющихся запросов; новые запросы ждут смены. Это предотвращает
гонку назначения с проверкой перед отключением в **одном процессе бота**.
Независимые активные bot workers с отдельными кешами этим механизмом не
синхронизируются; gate внедрения должен подтвердить единственный активный процесс.
Не масштабировать на несколько writers без общей authoritative revision/fence.

Область управления — существующая конфигурация экземпляра. Не добавлены
организационные роли, новый employee registry, Workspace adapter или разрешения
на чужую организацию. Существующие OrgRef/ClientProfile/routing bindings и
fail-closed Workspace integration сохраняются. Этот кандидат не объявляет
незавершённую межорганизационную интеграцию реализованной.

Незавершённое подключение ограничено 15 минутами, привязано к actor/chat/topic
и хранится только в памяти. После рестарта его нужно начать заново. Сохранённые
роли/состояния восстанавливаются существующим initStaffCache из YAML.

## Локальная проверка и ограничения доказательств

Установка: `npm ci --ignore-scripts`; native runtime addons не запускались.
Окружение editor: Node 22.23.2; репозиторий и штатный CI требуют Node 24.
Финальная команда проверки: `npm run build && npm test`.
Результат: TypeScript build PASS; финальный полный npm test — 73 suites,
922 tests PASS (14.255 s). Это локальные проверки Node 22, не CI Node 24,
не GUI и не production restart.
Контрольные суммы файлов кандидата: `ENGINEERS_RBAC_CANDIDATE.sha256`
(не заменяют точный Git SHA и независимое ревью AOR).

Добавлены тесты YAML persistence/reload, прав, owner/self protection, verified
identity, отключения с активной работой, CAS/повторов/конкурентных записей, отката,
отзыва старых callback/незавершённого ввода, DM-входа и read/write barrier.
Полная штатная suite дополнительно проверяет существующие lifecycle/privacy/
client bindings/routing/return-to-common регрессии.

Проверить Git history, PR48 и связанные PR из editor не удалось: `/usr/bin/git`
возвращает `Permission denied`. Обход запрета не предпринимался. Поэтому
актуальность remote base/связанных работ и точный release SHA подтверждает AOR.
Коммиты editor не создавал. CI и независимое ревью editor не запускал вручную.

## Gate для штатного AOR

1. Проверить историю/remote/связанные работы и diff относительно checkpoint;
   исключить дублирование уже выпущенного. Зафиксировать точный кандидат SHA.
2. Обязательный MOST Core CI (`.github/workflows/most-core-ci.yml`) на Node 24:
   `npm ci`, build, полный npm test. Результат относится к этому точному SHA.
3. Независимое ревью того же кандидата штатным диспетчером: проверить роли,
   single-process fence, identity trust, YAML CAS/rollback, старые intents,
   все командные маршруты и отсутствие расширения организационного доступа.
4. Отдельное подтверждение владельца на внедрение и изменение только заранее
   согласованных тестовых ролей. До него VM3902 не изменять.
5. Штатная trusted activation exact release и проверка materialized tree,
   затем GUI на VM4090. До фактических результатов цель бизнеса не завершена.

Статус этих внешних gate: **ожидают AOR / владельца; не пройдены editor**.

## Воспроизводимый GUI-сценарий Telegram Desktop, VM4090

До начала выделить согласованные тестовые аккаунты: A (admin, не единственный),
S (supervisor), E (agent), C1/C2 (клиенты разных тестовых организаций), нового E2.
Названия тестовых заявок: `RBAC-20261117-<run>-<case>`. Только эти сущности.
Не пересылать реальные клиентские сообщения и не трогать существующие чужие роли.
Владельца и последнего admin проверять на изолированной тестовой конфигурации,
не экспериментом над действующим production доступом владельца.

1. A: /start в личном чате → «Инженеры». Проверить несколько страниц и карточку.
   Изменить имя E2, проверить экранирование, повторно открыть раздел.
2. E2 отправляет согласованное тестовое сообщение A; A пересылает его боту через
   «Подключить инженера». Сверить ID, подтвердить. Доступ E2 ещё отключён.
   Проверить отказ для @username, скрытого автора и повторного подтверждения.
3. A выбирает E2 → уровень agent → подтверждение → включить → подтверждение.
   E2 делает /start. Затем A повышает E2 до supervisor, проверяет распределение
   и аналитику; E2 не должен видеть/исполнять управление командой. Вернуть agent.
4. C1 создаёт только тестовое обращение. E берёт его; проверить ответ клиента
   без личности инженера, запись работ, передачу E2, закрытие с причиной/работами
   и возврат в общие через существующую политику. Отдельно проверить ручную заявку.
5. При активном назначении/предложении E2 отключение отклоняется. Передать работу
   согласованному тестовому инженеру/контролируемо вернуть в общие. Отключить E2.
   Его старые take/reply/transfer/management buttons и незавершённый ввод не дают
   действий. Повторный /start не восстанавливает роль. Проверить повтор кнопки A.
6. Проверить запреты S/E/C на изменение команды, повышение себя; C видит только
   свои обращения; E не видит чужую личную заявку; C2 не видит C1 и другую org.
   Не считать отказ одной кнопки доказательством всех командных путей.
7. A: открыть два подтверждения, сохранить одно, второе должно устареть.
   Откатить последнее изменение; проверить карточку, YAML audit через штатного
   оператора без выгрузки конфигурации/токенов в чат. Провести согласованный
   restart через AOR, проверить сохранённые роли и повторный вход.
8. На изолированной конфигурации: попытки отключить/понизить владельца,
   изменить собственные полномочия и убрать последнего admin должны отклоняться.

Фиксация: для каждого шага записать run ID, release SHA, UTC, псевдоним аккаунта,
роль до/после, ID только тестовой заявки, ожидаемое/фактическое, PASS/FAIL/BLOCKED,
ссылку на скриншот Telegram Desktop (с очищенными посторонними чатами/данными).
Не сохранять токены, конфигурацию целиком или реальные переписки. Для restart
нужно отдельное evidence до/после. Итог GUI — подписанный владельцем/оператором
протокол; отсутствующий шаг остаётся NOT RUN, unit tests его не заменяют.
