# Пострелизный кандидат: навигация и Rich HTML demo

Подтверждённый кодом сценарий: `/start` открывает `mine:0`; повторная кнопка
`tm:mine:0` раньше давала пустой ACK, а renderSignature или Telegram
`message is not modified` подавляли видимый edit. Это один сценарий, а не
доказательство единственной причины жалобы владельца. Теперь выбранная вкладка
отмечена `✓`, переход/обновление в DM имеет текстовый ACK, данные и счётчики
перечитываются. Неизменившаяся панель не дублируется.

`👁 Пример Rich HTML` в личной панели отправляет одну синтетическую карточку
через общий renderer и Telegram transport независимо от глобального opt-in.
Тикеты не читаются. Guard активного сотрудника и собственного DM применяется
в callback. Подтверждённый отказ rich или отсутствие SDK метода дают classic
с явной пометкой. UNKNOWN не вызывает повторную отправку. Успех API не
доказывает фактический rich render клиента.

## Ручная проверка владельцем после отдельного разрешения на выкладку

1. В DM активного сотрудника выполнить `/start`: увидеть выбранную «Мои в работе».
   Нажать её снова и «Обновить»: увидеть ACK, одну панель, актуальный счётчик,
   свои активные заявки либо «Заявок нет».
2. Перейти «Общие» → «Мои в работе», затем «Ожидают принятия» → «Мои в работе».
   Сверить список и счётчик; личные заявки другого инженера не должны появиться.
3. Из разрешённой рабочей темы открыть старую кнопку `tm:mine:0`: результат
   должен прийти только в DM; в группе не должно быть личных списков/счётчиков.
4. В DM нажать «👁 Пример Rich HTML»: увидеть «Демо» с вымышленными данными.
   Зафиксировать клиент/версию и фактический вид Bubble. Classic с пометкой
   недоступности не считать успешным rich render. При неопределённом исходе
   не повторять отправку автоматически.
5. У клиента, отозванного сотрудника и в группе demo недоступно.

Production config/opt-in, owner/visibility/CAS и предыдущий scope не меняются.
Live Telegram, merge/release/deploy в рамках редакторской задачи не выполняются.
Независимый штатный AOR APPROVE, создание нового SHA, CI этого SHA и публикация
кандидата выполняются оркестратором после передачи файлов; локальные проверки
не заменяют эти этапы.
